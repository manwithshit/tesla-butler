# 默认电价与充电批次成本分摊设计

## 目标

行程成本不再使用“本周期账单平均价 × 本周期全部电耗”。用户设置一项日常默认电价；每张已确认且可靠关联到 TeslaMate 充电记录的账单形成一个实际价格批次。后续行程按时间顺序先消耗这些批次，批次耗尽后的普通电量使用当时有效的默认电价。

这是本地费用分摊估算，不追踪物理电子。TeslaMate 继续作为行程、充电时间和车辆能耗的事实来源；飞书账单只提供当次实际支付金额和购电量。

## 用户体验

- 新安装尚无飞书会话，Worker 启动时不主动推卡。
- 用户第一次打开“菜单/帮助”时，如果默认电价仍为空且从未提示，先返回正常菜单，再展示一次设置卡。
- 设置卡发送成功后才记录“已提示”；失败会在下次打开菜单时重试。
- 自动提示只出现一次。菜单永久保留“默认电价”入口，可随时查看或修改。
- 首次设置用于补算既有的未定价行程；以后修改只影响修改时刻之后的普通电量，不改写过去。
- 表单只接受 0 至 10 元/度、最多四位小数。随手发送的普通数字不会被当成电价。

## 账本模型

`data/processed/receipts.json` 在现有 `receipts` 根键旁增加：

```json
{
  "pricing": {
    "schema_version": 1,
    "default_rate_history": [
      {
        "price_cny_per_kwh": 0.6,
        "effective_at": "1970-01-01T00:00:00.000Z",
        "recorded_at": "ISO timestamp",
        "source": "user_feishu_form"
      }
    ]
  }
}
```

首次设置的 `effective_at` 为全历史起点；后续记录的 `effective_at` 为实际修改时间。历史记录只追加，不覆盖。

特殊价格批次由现有账单事实确定性推导，不另存可变余额：

- 账单必须 `confirmed`；
- 必须可靠关联并选中一个 charging process；
- 批次可用时间为对应充电结束时间；
- 批次电量为账单识别并经用户确认的电量；
- 批次综合单价为实付金额除以账单电量；
- 同一 charging process 最多产生一个批次。

未关联账单仍保留在账本和账单统计中，但不参与行程成本分摊，避免猜测它应从哪一趟开始生效。

## 分摊规则

1. 按充电结束时间和行程开始时间重放完整时间线。
2. 每趟行程先按 FIFO 消耗当时已可用的特殊价格批次。
3. 行程剩余电耗按该时刻有效的默认电价计算。
4. 高价、低价和免费账单采用相同规则；便宜账单相对默认价可以形成负调整，但实际成本不为负。
5. 批次余额由完整事件重放得出，跨行程、跨周月和 Worker 重启不会重置。
6. 迟到但成功关联的账单会按真实充电结束时间回溯重算后续行程；已经发送的旧卡不会自动撤回，新查询会显示校准后的结果。
7. 任一相关行程缺失可靠电耗时，不伪造完整成本；界面显示“暂不可算”。

## 一致性与安全

- 所有账单和定价写入共享同一串行队列，避免并发事件互相覆盖。
- 同值重复提交幂等，不新增历史版本。
- 表单回调按精确的 action name 处理；不记录输入原文。
- 卡片与日志不包含会话标识、车辆标识、坐标或凭证。
- 不修改 TeslaMate，不向车辆发送任何命令。
- 当前试用环境按单车验收；检测到多辆车且存在特殊价格批次时会停止费用分摊并明确显示暂不支持，绝不跨车混算。

## 已知后续优化

当前会从最早一张特殊价格账单开始重放后续行程。随着多年轨迹累积，查询时间会线性增长；正式扩展前应增加逐行程能耗缓存和带输入校验的重放检查点。

## 本次发布边界

功能只在 M1 本地分支开发、测试，随后合入 M1 本地 `main` 部署观察。暂不推送、不更新远端 `origin/main`；试用确认后再决定是否发布。
