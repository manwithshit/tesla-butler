# 安装授权与本地 OCR：决策交接

> 日期：2026-08-25  
> 状态：Apple Vision 主链路已在 M5 实施；多平台与 macOS 13 验收未完成  
> 适用范围：Mac 用户、macOS 13 及以上  
> 后续 Agent：开始修改前先读完本文，再重新检查当前代码、文档和运行状态；本文记录的是决策基线，不代表代码已经切换完成。

## 一、当前结论

1. 产品可以明确限定为 Mac-only，不需要为 Windows 或 Linux 增加 1.0 兼容层。
2. 用户入口目标为 `npx <package-name>` 一键安装和启动引导；最终包名尚未确定。
3. 默认安装路径不应要求用户提供 K3、Kimi 或其他视觉模型 API Key。
4. 充电账单优先使用 macOS Apple Vision 本地 OCR，再用确定性规则完成字段配对和校验。
5. K3 已降级为可选兜底：只有本地 OCR 关键字段缺失、确定性校验失败或遇到未知版式时才调用。
6. 默认安装不要求 K3；只有环境中明确配置 `KIMI_BASE_URL` 时才启用兜底。
7. 月度主跑路线、开始充电提醒、即将达到设置上限提醒都可以完全使用 TeslaMate、MQTT 和本地确定性代码，不需要 K3。

`npm` 与 `npx` 的定位不同：项目仍通过 npm 包分发；普通用户使用 `npx` 直接运行安装器，不需要先全局安装命令行工具。目标体验是用户只复制一次 `npx` 命令，后续检查、下载、配置和启动由安装器引导完成。

## 二、需要用户主动完成的授权

面向用户时，把“业务授权”和“本机环境确认”分开表达，避免把所有系统弹窗都说成授权。

### 业务授权：两项

1. **连接飞书机器人**
   - 用户完成飞书 CLI／自建机器人绑定，以及飞书侧必要的应用确认。
   - 只申请接收单聊消息、读取图片资源、以机器人身份回复和发送卡片所需的最小权限。
   - 不申请通讯录、文档、日历、全量群聊或用户身份权限。

2. **连接 Tesla 数据**
   - 用户只在 Tesla 官方登录页或本机授权工具中输入账号、密码和 MFA。
   - Token 只交给本机 TeslaMate，不发送到 Agent 对话、项目方服务器、Markdown、Git 或日志。
   - Owner API Token 不能对外描述成细粒度“只读 Token”；产品保障应表述为：自研代码只读 TeslaMate PostgreSQL，不调用任何车辆控制命令。

### 本机环境确认：不算业务授权

Docker／本地容器运行时继续保留。首次安装可能出现系统确认、辅助组件安装、磁盘空间或后台运行提示。这些步骤需要用户点击，但应明确说明它们不是在授权项目读取账号或控制车辆。

安装器在触发确认前必须先告诉用户：

- 为什么需要：在本机运行 TeslaMate、PostgreSQL 和 MQTT。
- 对电脑的影响：会创建本地容器、数据库和后台服务，占用一定磁盘与内存。
- 不会做什么：不会把车辆数据上传到公共服务器，不会读取无关文件，不会发送车辆控制命令。
- 如何停止或卸载：提供可见、可复制且不删除车辆数据的停止方式；删除数据必须二次确认。
- 拒绝后的结果：退出安装并说明哪些功能无法运行，不把取消描述成错误。

## 三、授权和安装文案原则

避免直接使用“请授权全部权限”“需要控制电脑”“粘贴 Token 给 Agent”一类表达。每一步使用同一结构：

1. **这一步要连接什么。**
2. **为什么需要。**
3. **会读取或保存什么。**
4. **明确不会读取或执行什么。**
5. **用户取消后会发生什么。**
6. **成功、失败和取消都给出明确结果。**

推荐的安装引导顺序：

1. 检查 Mac 型号、macOS 版本、Node.js、Docker 和磁盘空间。
2. 展示本地运行与隐私说明。
3. 安装或启动本地依赖。
4. 引导连接飞书机器人。
5. 在本机打开 Tesla 授权工具。
6. 启动 TeslaMate、PostgreSQL、MQTT 和项目 Worker。
7. 显示逐项健康检查结果。
8. 明确提醒：授权完成不等于已有历史数据；只有 Mac 保持运行、联网并持续采集，之后的新行程才会进入系统。

安装器必须可重复执行，已完成的步骤自动跳过或安全校验；失败后给出有限重试、明确原因和恢复入口，不能停在无反馈状态。

## 四、Apple Vision OCR 实测结论

### 测试素材

- 3 张用户提供的真实充电订单截图。
- 分辨率均为 `1170 × 2532`。
- 三张属于同一个充电平台、相同页面版式。
- 本轮只输出白名单字段和命中结果，没有把订单号、位置或其他敏感文本写入日志。

### 结果

| 方案 | 图片结果 | 核心结构化字段 | 单张耗时 |
|---|---:|---:|---:|
| Apple Vision 本地 OCR | 3/3 正确 | 电量、电费、服务费、总计共 12/12 正确配对 | 0.16–0.55 秒 |
| K3 | 3/3 正确 | 同样 12/12 正确，未把广告误认成运营商 | 16.4 秒、134.6 秒、21.2 秒 |

Apple Vision 还完成了以下验证：

- 8 个关键标签和 5 组关键数值在三张图中全部命中。
- 使用标签与右侧同一行坐标做确定性配对后，核心字段仍为 12/12 正确。
- 当前样本下，本地 OCR 无需模型理解即可得到可用结构化结果。

### 推荐识别链路

1. Apple Vision 使用 `.accurate` 级别识别中文和英文。
2. 只保留允许进入账单的字段，不保存或输出整张图片的完整 OCR 文本。
3. 根据标签、坐标和金额格式确定性配对。
4. 校验金额范围、费用拆分、总额关系和字段完整性。
5. 结果交给用户确认；确认前不得写入正式账本。
6. 本地结果低置信度或关键字段缺失时，再进入可选 K3 兜底。
7. K3 不可用或用户未配置时，仍要返回明确失败原因，并允许用户稍后重试；不能要求用户手工输入账单数据。

### 尚未证明的部分

- 目前只有 3 张同版式样本，不能据此宣称支持所有充电平台。
- 尚未覆盖特来电、星星充电、国家电网、Tesla 超充等不同版式。
- Apple Vision 识别能力支持 Mac 本地方案，但当前耗时和准确率只在本轮 M5、当前 macOS 环境实测；macOS 13 真机仍需单独验收。
- 需要补充裁切、模糊、深色模式、低分辨率、长截图和字段缺失等失败样本。

因此，当前决策是“值得切换、本地优先”，不是“已经可以删除 K3”。

### 2026-08-25 实施验证

- 已增加预编译 Apple Vision helper、本地字段解析器、确定性校验和 K3 可选兜底。
- 用真实充电账单截图完成主链路验证：实付 `¥21.85`、电费 `¥13.36`、服务费 `¥8.49`、综合单价 `¥1.39/度`、结束时间 `19:29` 和推算电量 `15.72 kWh` 均与截图一致。
- 首次运行包含 helper 编译约 `5.3 秒`；编译后同图实测约 `365 毫秒`。
- 本次输出只包含白名单字段和验证结果，未打印完整 OCR 文本、车牌、地点或订单信息。
- 该验证仍只覆盖当前这一种订单版式，不扩大为多平台支持结论。

## 五、不需要 K3 的新增功能

### 月度主跑路线

- 数据来自 TeslaMate 已完成行程。
- 使用起终点距离、往返合并、重复次数和累计里程做本地聚类。
- 当前规则为端点 750 米内归组，至少重复 3 次才显示主跑路线。
- 当前真实数据只有 4 段候选行程，尚未形成可代表性验收的主跑路线。

### 开始充电提醒

- 使用 TeslaMate MQTT 的 `charging_state` 状态变化触发。
- 每个充电会话最多发送一次。
- 不需要模型生成文案，使用固定模板即可。

### 即将达到设置上限提醒

- 优先使用 `time_to_full_charge <= 0.25` 小时。
- 剩余时间缺失时，使用当前电量距离 `charge_limit_soc` 不超过 5% 的降级规则。
- 文案必须写“达到设置上限”，不能写“充满”。
- 不需要模型推理或生成。

## 六、当前 Review 状态

1. **新充电会话继承旧快照：已修复。** 新会话会清除不属于当前会话的 ETA、功率和已充电量；即将达到上限提醒只接受两分钟内的新数据，并在发送前再次确认仍处于当前充电会话。
2. **提醒发送失败后可能永久丢失：尚未修复。** 当前状态先持久化为已触发，再尝试发送飞书；发送失败后不会自动补发。应使用相同幂等键有限重试，并在成功后确认发送状态。
3. **主跑路线地图失败会被误报为路线分散：尚未修复。** 地图渲染或上传失败时不应丢弃已经算出的路线统计，只应降级隐藏图片并保留文字结果。

当前自动化测试已覆盖旧 ETA、新鲜度和发送前状态复核；测试总数以最新 `npm test` 输出为准。下一次真实充电仍需验证开始提醒、暂停恢复、达到上限提醒和 Worker 重启后的端到端行为。
